# Common 数据持久化与同步方案（V1）

版本：V1（2026-01-15）
适用范围：本仓库 `common` 子项目内的 Drift/SQLite 数据表及其远端同步（persistence_* + Firebase/Firestore）

---

## 1. 背景与目标

### 1.1 背景
当前项目已完成 `persistence_core / persistence_drift / persistence_firebase` 的基础整合，并在 `layout_template` 上形成了“本地写入 + outbox 入队 + 远端 push + 远端 pull 回填 + 冲突处理”的样板闭环。

`common` 中存在两类明显不同的数据：
- 用户私有数据：按用户隔离，支持多端同步与冲突处理。
- 全局/公共数据：所有用户可读，但写入权限应严格受控；同时部分公共数据允许用户“在自己空间里扩展/覆盖”。

此外，存在一些表使用自增主键或纯关联表结构，若直接同步会出现“跨设备主键冲突/幂等失败”等问题，需要引入“稳定主键”策略。

### 1.2 目标
- 将 `common` 中“需要多端一致”的用户数据，统一接入 persistence_* 的同步闭环（push/pull）。
- 将“公共可读”数据以 Firestore 公共集合方式（pull-only）分发，支持快速迭代与启用/禁用。
- 对“用户可自定义的公共类数据”（如 DivinationTypes/SubDivinationTypes/SkillClasses 及其映射），采用“全局默认 + 用户覆盖层（overlay）”模型，既保留默认值，也支持用户自行维护。
- 引入稳定主键策略，解决多端同步下自增主键与映射表幂等问题。
- 保留未来技术切换的可能：公共数据未来可从 Firestore pull-only 切换为 Storage bundle 导入，但业务层/DAO/上层使用方式尽量不变。

## 2. 当前存储方案（现状盘点）

### 2.1 本地存储（Drift/SQLite）
`common` 使用 Drift 维护业务本地库（`AppDatabase`），包含：
- 用户资产类：Divinations/Panels/Seekers/TimingDivinations 等
- 业务配置类：LayoutTemplates/CardTemplate* 等
- 字典类：Skills/SkillClasses/DivinationTypes/SubDivinationTypes/DivinationSubDivinationTypeMappers 等

数据库初始化：通过 `assets/sql/initial_data.sql` 在首次创建库时导入默认字典数据。

### 2.2 同步引擎（persistence_*）
- `persistence_drift`：本地 outbox 与 sync_state（cursor）存储。
- `persistence_core`：同步协调器（pushOnce/pullOnce）与运行时调度（SyncRuntime）。
- `persistence_firebase`：RemoteGateway 的 Firestore 实现（push/pull 协议落地）。

已验证样板（LayoutTemplate）：
- 本地更新后写入业务表 + enqueue outbox（entityType=`layout_template`）
- 远端按 cursor 拉取 RemoteChange
- 本地 LocalApplier.applyRemoteChanges 回填，采用 LWW（按 updatedAt/deletedAt 规则）

## 3. 关键设计决策（为什么这样做）

### 3.1 按“数据归属”拆分同步通道：Public vs User
**为什么：**
- 同步引擎以 `scopeUid` 作为隔离单元。用户数据的 scope 是 `appUserId`；公共数据不属于某个用户，应使用公共 scope 或公共路径。
- 若混用同一路径，会出现权限规则复杂、数据桶混乱、以及公共更新可能覆盖用户自定义的风险。

**好处：**
- 安全模型清晰：公共数据 read-only，用户数据按 appUserId 隔离。
- 运行时调度清晰：公共同步固定 scope；用户同步随 active account 切换。
- 未来切换公共数据来源（Firestore ↔ Storage bundle）时影响面最小。

**解决的问题：**
- 避免把“所有人共享”与“每人私有”混在一个数据流里导致的权限与数据一致性问题。

### 3.2 “全局默认 + 用户覆盖层（overlay）”而不是“同表 isCustomized 区分”
适用对象：
- SkillClasses
- DivinationTypes
- SubDivinationTypes
- DivinationSubDivinationTypeMappers
（以及未来可能新增的类似字典+用户自定义场景）

**为什么：**
- 同表混合会导致：公共更新与用户自定义写入发生冲突、查询逻辑复杂、权限规则难写（客户端写公共集合不允许）。
- overlay 将“默认字典”和“用户选择/自定义”分离，公共更新不会覆盖用户意图。

**好处：**
- 默认内容可被全局更新，用户自定义独立演进。
- 用户可以“禁用/覆盖默认项”而不修改默认项本体。
- 同步策略可分别优化：默认项 pull-only；用户项 push+pull。

**解决的问题：**
- 公共字典更新覆盖用户配置、以及多端合并时的冲突与权限难题。

### 3.3 稳定主键（Stable EntityId）策略：解决自增主键与映射表幂等问题
**为什么：**
- 自增主键在多端并行插入时不稳定（A 端 id=1 与 B 端 id=1 语义不同）。
- 映射表（多对多/关联表）若使用自增 id，则无法自然幂等合并，远端 docId 也难以确定。

**好处：**
- 同一业务对象在不同设备上可生成一致的 entityId，支持幂等 upsert。
- 冲突策略可集中到业务字段（updatedAt/deletedAt），而非被主键问题干扰。

**解决的问题：**
- 多端同步下主键冲突、重复插入、无法幂等重放导致的数据漂移问题。

## 4. 数据分区与访问模型（V1）

### 4.1 同步分区一览
#### 4.1.1 Public Sync（公共数据，pull-only）
- 远端：Firestore 公共集合（示例路径：`public/modules/common/{entityType}/{entityId}`）
- 客户端：只拉取（pull），不产生 outbox/push
- 权限：全用户可读；客户端不可写（仅管理员/云函数可写）

包含：
- Skills（全局定义）
- SkillClasses（默认集）
- DivinationTypes（默认集）
- SubDivinationTypes（默认集）
- DivinationSubDivinationTypeMappers（默认集）

#### 4.1.2 User Sync（用户数据，push+pull）
- 远端：`users/{appUserId}/modules/common/...`
- 客户端：本地写入后 enqueue outbox，push 到远端；远端变更 pull 回填本地
- 权限：仅当前用户可读写自身桶

包含：
- 用户资产数据（Divinations/Panels/Seekers/TimingDivinations/…）
- 配置类数据（LayoutTemplates/CardTemplate* 等）
- 用户自定义字典（SkillClasses/DivinationTypes/SubDivinationTypes/DivinationSubDivinationTypeMappers 的用户维护集）
- 用户 overlay（例如：禁用默认项、排序、别名等）
- 用户权益/购买（见 4.3）

### 4.2 运行时调度建议
V1 推荐运行两套 runtime（概念上）：
- `PublicRuntime`：scopeUid 固定（例如 `'public'`），仅 pull 公共 entityTypes。
- `UserRuntime`：scopeUid = active `appUserId`（支持 guest），push+pull 用户 entityTypes。

备注：两套 runtime 可共享同一个 RemoteGateway 实例，但 RemoteGateway 需支持 public 与 user 两类 entityType 的路径映射。

### 4.3 Skill 的“全局定义 + 用户权限”模型
#### 4.3.1 SkillCatalog（公共）
- Skills 作为全局能力/商品定义：所有用户可读（pull-only）。

#### 4.3.2 UserSkillEntitlement（用户私有）
- 每个用户拥有的 skill 列表（购买/授权结果）。
- 安全要求更高：建议客户端只读，写入走云函数/支付回调。
- 业务可用性：`skill 可使用 = skill 在 catalog 存在且 entitlement 包含该 skill`。

## 5. Public 数据的技术选项与当前选择

### 5.1 技术选项
#### 选项 A：Storage bundle + 本地导入（批量包）
- 优点：更新成本低，适合大批量字典；客户端读放大低。
- 缺点：增量粒度粗，需要下载包；需要额外的版本管理与校验。

#### 选项 B：Firestore 公共集合 + pull-only 增量同步
- 优点：增量更新天然支持；快速开发；无需维护 bundle 生产链路。
- 缺点：数据量大时读放大；规则/索引设计复杂度略高。

### 5.2 当前选择（V1）
选择：**选项 B（Firestore 公共集合 + pull-only）**
原因：
- 目标优先“快速开发、可迭代启用/禁用”；
- 可直接复用 persistence_* 的 pull/cursor/回填框架；
- 后续可切到选项 A：只需替换 PublicCatalogSource 的实现，不影响用户数据同步与业务层。

## 6. Stable EntityId（稳定主键）策略（V1）

### 6.1 三类表的主键策略
#### 类型 1：实体表（用户创建的业务对象）
- entityId：UUID/ULID（创建时生成，跨设备稳定）
- 示例：Divinations.uuid、Panels.uuid、Seekers.uuid、LayoutTemplates.uuid

#### 类型 2：映射/关联表（多对多、关系定义）
本地：
- 使用复合唯一约束提升查询与去重（例如 `(leftId, rightId, ownerScope)`）。
远端：
- 使用确定性 entityId 作为 Firestore docId 与同步主键。

确定性 entityId（推荐规范）：
- canonical string：
  - `key = 'v1|{entityType}|scope={scope}|a={aId}|b={bId}'`
- hash：
  - `entityId = base64url(sha256(utf8(key)))`
- 说明：
  - scope 对公共数据固定为 `public`（或空但建议固定）；
  - scope 对用户数据为 `appUserId`；
  - 对有方向的关系固定拼接顺序；
  - 对无方向的关系先对 (aId,bId) 做字典序排序再拼接。

适用示例：
- DivinationSubDivinationTypeMappers（typeId, subTypeId, scope）
- PanelSkillClassMappers（panelUuid, skillClassUuid, scope）

#### 类型 3：事件/日志表（append-only）
- 每条事件生成 `eventId`（UUID/ULID）
- 若需要多端可见（同步）：本地与远端均以 eventId 为主标识（强烈推荐）。
- 若仅远端汇总（不需要多端可见）：可只 push 不 pull，但仍建议 eventId 用于去重与幂等补发。

## 7. DivinationTypes/SubDivinationTypes/Mapper 的最终模型（V1）

### 7.1 默认集（Public）
- DivinationTypes（默认）
- SubDivinationTypes（默认）
- DivinationSubDivinationTypeMappers（默认）

特点：
- pull-only
- 客户端不可写
- 允许 enabled/disabled（由服务端/运营控制）

### 7.2 用户维护集（User）
用户可新增/编辑/删除：
- DivinationTypes（用户自定义）
- SubDivinationTypes（用户自定义）
- DivinationSubDivinationTypeMappers（用户自定义）

并允许用户对默认集做“覆盖/禁用”（建议用 overlay）：
- 禁用默认 type/subtype
- 禁用默认 mapping
- 用户自定义 mapping 优先级高于默认 mapping

### 7.3 引用口径（避免混淆默认与用户数据）
- 任何“映射关系”两端都使用“逻辑 ID”（默认项 uuid 或 用户项 uuid）
- 映射中需要能区分引用来源（public/user），推荐引入 namespace 概念（实现时可用字段或约定前缀）。

## 8. 安全与权限（Firestore Rules 口径）

### 8.1 公共集合
- 允许所有用户 read（可选：必须已登录）
- 禁止客户端 write（仅管理员/云函数）

### 8.2 用户集合
- 用户只能读写 `users/{appUserId}/...` 下与自己 identity_map 映射一致的桶
- 避免使用 baasUid 直接做业务分桶；业务统一使用 appUserId

### 8.3 Skill 权益（entitlement）
- 读：用户只读自己
- 写：建议仅云函数可写（客户端禁止写），避免伪造购买权限

---

## 9. 迁移计划（稳定主键落地）

### 9.1 阶段 1：加列回填（先跑通同步）
- 映射表：新增 `stable_id` 并按确定性规则回填；新增复合 unique index（若历史存在重复需先清理）。
- 事件表：新增 `event_id` 并回填 UUID；新写入必须生成 event_id。
- 同步层：entityId 一律使用 stable_id/event_id。

### 9.2 阶段 2：约束收敛（提升一致性）
- 将 stable_id/event_id 提升为唯一键或主键（视 Drift 迁移复杂度选择）。
- 逐步移除对自增 id 的外部引用与跨表依赖。

---

## 10. 验收标准（V1）

- 公共默认字典可通过 pull-only 从 Firestore 增量更新到本地。
- 用户可在自己的空间里维护 DivinationTypes/SubDivinationTypes/DivinationSubDivinationTypeMappers，并可同步到多端。
- SkillCatalog 全用户可读；用户是否可使用由 entitlement 决定且权限安全。
- 映射表与事件表具备稳定 entityId/eventId，确保幂等同步与多端一致。
- 未来可将 PublicCatalogSource 切换为 Storage bundle 导入，而不影响用户数据同步与业务层调用方式。
